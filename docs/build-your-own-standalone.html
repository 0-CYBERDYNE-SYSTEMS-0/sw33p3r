Build Your Own Standalone Survey Device

Four architectures to recreate Room Sweep's detect-only mission (sub‑GHz CC1101 scan · WiFi/BLE survey · GPS logging · session logs) on hardware that is not a Flipper and not running Momentum.

🧭 What Room Sweep Actually Needs From Hardware

The trick is that none of these radios can transmit in your design — you either leave radios physically RX-only (omit the TX path / control regs) or simply never issue transmit commands. That's the whole point of staying within the MISSION.md contract.

🏗️ Architecture 1 — Single-Chip ESP32-S3 (Recommended)

The most faithful standalone recreation. WiFi and BLE are already on the same silicon as the CPU, so there is no second processor, no UART handoff, and no separate Marauder firmware — you write one C program that reads CC1101, scans WiFi/BLE, logs to SD, and draws the UI.

Wiring (if not using a pre-integrated board)

 CC1101 module          nRF24L01 module        Display (e.g. ST7789/ILI9341)
  ------------------      -----------------      ------------------
  MOSI/SCK/MISO/CS ─────► shared ESP32 SPI      (second SPI controller or addl CS)
  GD02 (GDO2) ──────────► GPIO (RX-ready IRQ)   backlight + touch/key fob

Unlike the Flipper — which shares one SPI bus between internal CC1101 and nRF24 and needs a hardware switch — the ESP32 has multiple SPI controllers and plenty of GPIO, so each radio gets its own CS. No bus arbitration needed. Both radios are driven by a small SPI driver (ESP‑IDF spi_master or Arduino SPI).

Firmware plan (all in one C project)

  • Framework: ESP‑IDF (C, closest to Room Sweep's style) or Arduino (fastest to prototype).
  • Sub‑GHz loop: SPI driver for CC1101; poke registers to RX on each band; read RSSI / OOK-FSK decode. Same radio work the current sub‑GHz engine does, minus the Flipper subghz API.
  • WiFi/BLE: ESP-IDF esp_wifi_scan + esp_ble_gap_scan — pure passive scans → per-AP / per-device RSSI list, exactly matching the Wi / BT tabs.
  • nRF24 RPD (optional): simple SPI channel-energy read.
  • Logging + GPS: esp_vfs_fat_sdmmc for the SD card; UART driver for GPS NMEA (you already have nmea.c — reuse it).
  • UI: LVGL or a light custom framebuffer for the small touch/OLED screen.
Why this is the cleanest: you fully own the code, so there are no attack modes by construction. Every radio only ever configures RX. It directly matches Room Sweep's features with no translation layer, and total BOM is ~$35–50.

Notable + shared pitfalls

  • CC1101 and nRF24 share SPI — each needs its own CS line. On the T‑Embed CC1101 there's only one CC1101, so add the nRF24 to a separate controller.
  • ESP32 real-time limits: use a dedicated task for the RF loop (RFID timing logic stays small, like the current <64-byte stack rule).
  • OOK/FSK decode is the hardest part — carry over your existing signal-decoding code rather than reinventing it.

🧰 Architecture 2 — Control MCU + Radio Modules (Flipper-style Split)

This mirrors how the Flipper itself is built: a small main MCU drives the sub‑GHz radios directly, and a separate ESP32 handles WiFi/BLE. The advantage is that you can reuse standard ESP32 firmware and the exact UART protocol Room Sweep already speaks, so you write almost no WiFi/BLE code.

The clever reuse: UART protocol parity

  Pico / STM32 ──UART/115200──► ESP32-C3 (runs Marauder)
      │   send: "sniffbeacon" / "sniffbt" / "stopscan"
      │   ←─  stream of AP/device scan results
      │
      ├──SPI──► CC1101  (sub‑GHz, you own the decoder)
      ├──SPI──► nRF24   (2.4 GHz RPD, you own the decoder)
      ├──► SD / display / buttons

Because Room Sweep already drives a Marauder over UART, this is the shortest path to parity. You reuse your existing UART command layer and NMEA parser verbatim.

Detect-only note

Marauder includes attack commands. You simply never send them — the controller only ever issues sniffbeacon, sniffbt, stopscan. The passive-scan firmware doing the work only ever receives. This is exactly how the current BFFB + Room Sweep setup stays clean.

Trade-off: two MCUs means more wiring, more code to integrate, and you still rely on Marauder's scan output formats. Only worth it if you specifically want to avoid writing your own WiFi/BLE scan code. Estimated BOM ~$20–30.

📡 Architecture 3 — Software-Defined Radio (Wideband)

SDR trades pocketability for coverage. Instead of discrete radios tuned to the three CC1101 bands, an SDR sees the whole spectrum at once.

PathHardwareBOMCoverageDetect-only?
RTL-SDR + Pi Zero 2 W RTL-SDR v4 (~$30) + Pi (~$15) + display ~$45–60 500 kHz – 1.7 GHz By design (no TX)
HackRF clone + PortaPack HackRF clone (~$100) + PortaPack H4M (~$80) ~$180–220 1 MHz – 6 GHz RX so long as you never key TX
PortaPack H4M with Mayhem All-in-one handheld, no Pi ~$180–220 1 MHz – 6 GHz RX unless you use TX tools

How it does "sweep"

  • rtl_433 on a Pi decodes a huge library of ISM-band protocols (OOK / FSK / rolling-code remotes, sensors) — plug-and-play sub‑GHz identification.
  • GNU Radio lets you build a custom continuous spectrum analyzer that sweeps the entire 1.7 MHz–1.7 GHz span in one pass — broader than any CC1101 device.
  • Mayhem firmware on HackRF + PortaPack adds a GUI spectrum analyzer, signal generator, and protocol decoders in a handheld.
Which to pick: if the goal is a truly broad survey ("is anything transmitting anywhere I can reach?"), SDR is the answer. If you need the CC1101-band decode depth, battery-portable audio/buzzer feedback, and a pocket form factor like Room Sweep, it's the wrong tool — SDR can't sit comfortably on the CC1101 API the way a CC1101 driver can.

🔄 Architecture 4 — Repurpose the BFFB as a Standalone

The BFFB is just an ESP32 + dual CC1101 + nRF24 + GPS + MicroSD on a board. Nothing in that hardware requires a Flipper — the Flipper is only there for power, display, and input. Standalone, it's already most of what Room Sweep needs.

  • Power it from a LiPo / USB-C directly to the ESP32's 3.3 V rail.
  • Drive it with your own ESP‑IDF firmware — the same CC1101 + nRF24 drivers and Wi/BT scan logic as Architecture 1, because the BFFB's MCU is an ESP32-WROOM.
  • UI: add a small I2C/SPI OLED or LCD (SVGA) + buttons, or run it headless over its UART to a serial terminal.
  • The onboard MicroSD + GPS become your session logger and locator.
Downside: the BFFB alone costs ~$146 and is often out of stock. You'd be paying a premium to shell a Flipper-only board and then not using a Flipper. Only a good pick if you already own one or can source it cheaply.

🎯 Recommendation

Start with Architecture 1 on a LilyGo T‑Embed CC1101 (~$30–45). It already ships with the CC1101, display, rotary input, battery, and MicroSD. Add a ~$2 nRF24 module if you want the 2.4 GHz RPD tab, wire a UART GPS if you want location logging, and write the firmware in ESP‑IDF. Because all radios live on one ESP32 and you own every line, you get detect-only by construction — no attack modes, no translation layer, and a BOM under $50.

If you only care about sub‑GHz decoding and already have decoders you want to keep in C, Architecture 2 with a Pico + CC1101 lets you reuse your existing NMEA parser and decoder code while leaning on off‑the‑shelf Marauder over UART for WiFi/BLE. If you want the widest possible spectrum survey, SDR is the complement — it just won't match Room Sweep's CC1101-band decode depth or pocket form factor.
